## 一、先理解全文在回答什么

### 1. 问题起点：一条“可信记录”如何变成一次“可依赖的任务决策”

设想一次海上搜索任务：无人机观察海面，无人潜航器采集水下信息，无人艇承担中继和融合，岸上服务参与协调。最后，无人潜航器要依据一份目标位置产品调整航线。这份产品可能经历了采集、传输、定位、融合、签名、共享和入账等多个环节。

传统机制分别能回答其中一些问题：签名是否有效，设备软件是否符合已知基准，数据经过了哪些处理，共享记录是否一致。但是，**“现在能否根据这份位置产品调整航线”还要求知道：观测是否符合物理事实、是否足够新、定位误差是否可接受、多个来源是否真的独立，以及谁有权允许这次行动。**

文章把这种从局部机制到具体任务使用之间的距离称为 **mission-trust gap，任务信任缺口**。一个签名正确的错误位置，仍可能引发错误决策；一条不可随意改动的历史记录，也可能已经不适合当前行动。

### 2. 中心观点：任务信任由多种不可相互替代的主张支撑

全文的中心论点可以表达为：**某个对象是否值得在此时、此情境下被用于某项任务，要由针对不同性质的证据共同支撑；区块链能够增强其中部分记录与协作环节。**

四种主张贯穿全文：

| 要论证的内容 | 直接问题 | 一个能说明边界的例子 |
|---|---|---|
| 观测有效性 | 测量是否可信地反映外部世界？ | 定位被欺骗时，健康设备也可能报告错误坐标。 |
| 承诺与来源完整性 | 数据版本及其记录的生成、传递、处理历史是否可核验？ | 有效签名可以保护一份包含错误坐标的声明。 |
| 账本与治理一致性 | 在给定故障模型和规则下，各方是否对有效记录与状态转换达成一致？ | 各副本可能一致地保存了一个错误输入。 |
| 任务使用适用性 | 这些证据是否足以支持当前用途、时限和后果等级？ | 同一张图可用于一般态势参考，却不足以支持紧急避碰。 |

这里的“不可替代”很关键：通过某一项检查，并不能抵消另一项必要检查失败。四类主张也不是要求所有系统按固定顺序运行四道流水线；不使用账本的架构，可以采用相应的数据库或审计机制，并将账本专属项标记为不适用。

## 第 1 章：Introduction——为什么需要“任务信任”这个问题

### 1.1 论证如何展开

本章先从空中、水面和水下平台的能力互补谈起，再指出能力协同会把不同环境、链路、故障模式和管理主体的依赖联系起来。任务输出不再是某一个节点的独立产物，而是跨越多个处理与管理边界的结果。

接着，作者用四类反例建立问题：签名正确但物理上不合理的数据；真实但已过时的观测；来自被捕获端点却被正确排序的账本记录；来源完整但不确定性过大、无法承担高后果用途的数据产品。它们的共同点是：**某项局部属性成立，而任务需要的组合条件尚未成立。**

最后，本章将零信任、远程证明、来源追踪、信任计算和区块链接到同一问题上，引出 OAL、CTG、证据画像及 CDUTP。

### 1.2 归纳了哪些文献，各自起什么作用

本章的文献承担四个不同角色。跨域导航、编队、搜索与路径规划研究，如 Hu 等的跨域导航和 Wei 等的 3U 协同系统研究 [1、2]，说明多平台协同具有明确任务价值。无人机、海洋及水下系统综述说明移动性、能源、声学时延、定位和恢复困难等运行条件；Hayat 等的通信综述 [8] 是其中的代表。

安全综述归纳欺骗、干扰、捕获、恶意路由、数据操纵等威胁，例如 UAV 防护综述 [16] 与水声网络安全综述 [18]。UAV 区块链及海事区块链综述 [22、32] 则说明已有方案如何使用账本进行身份、共享和审计，以及相关资源和治理约束。

零信任架构 [39]、RATS [41]、W3C PROV [44、45] 和信任管理研究 [48–53] 提供可连接的基础机制。作者的整合在于：把这些机制放到“同一个任务对象、同一个使用时点、同一个具体主张”下审视。

### 1.3 本章表达的观点及其承接

题目中的 **Blockchain-Assisted** 应理解为“区块链辅助”。本文赋予区块链的作用，是加强某些共享记录、版本和审计关系；任务信任的定义先于账本选型。后续章节要回答的正是：如何将这个中心判断变成具体的分类、决策和评价方法。

## 第 2 章：Review Scope and Analytical Lens——本文的文献结论是怎样形成的

### 2.1 方法的核心是“主张—对象—情境”

本章将文章定位为**叙述性、问题驱动的概念综合**。分析单元不是简单的一篇论文，而是一个“主张—对象—情境”组合：研究评估了哪个对象的什么性质，处于哪个阶段，在什么链路、威胁与治理假设下，用什么证据得到结论。

这样做直接影响比较方式。例如，一个在岸上服务器运行的共识原型可以支持该配置下的吞吐量结论；能否移植到长期断联且电量有限的水下平台，需要重新检查前提。迁移的是候选机制，目标环境中的性能需要另行验证。

### 2.2 文献范围和检索方式

主要发现窗口覆盖 2016 年至 2026 年 8 月 6 日的英文资料，同时补充声誉、分布式系统、来源和共识等早期基础工作。资料类型包括同行评审论文、综述、学术书籍、标准及官方技术参考。

检索围绕六组主题：UAV 区块链与集群安全；海事和水下通信安全；UAV–USV–UUV 异构协同；IoT 信任与声誉；来源、远程证明和零信任；许可账本架构与治理。32 条 OpenAlex 查询每条最多获取 25 条按相关性排序的结果，并按 DOI 或 OpenAlex 标识去重，再结合种子综述和引用追踪。

这种设计适合为概念整合选取代表性机制。由于查询条数、每条结果上限、语言和选择方式均有边界，不能据此估计整个领域某类方法的比例。

## 第 3 章：Operational Context and Trust Foundations——建立全文共同的概念基础

### 3.1 跨域异构具体体现在哪里

UAV 适合快速机动、无线中继和光学观测，但受续航、载荷和链路稳定性约束；USV 可承载较大的能源与计算资源，连接水声和无线网络；UUV 贴近水下目标，却常受低速声学链路、短程光学通信或延迟上浮传输约束。海事通信与水下物联网综述 [54、59] 在这里提供环境依据。

更深一层的依赖来自多角色集中：一艘 USV 可能同时提供导航参考、数据缓存、通信中继、融合和账本服务。一处故障因此可能同时影响时间、链路、来源及共享状态。平台数量增加是否带来更强保证，要看关键依赖是否真正分散。

管理异构也属于系统条件。政府、研究机构、服务商和不同平台所有者可能分别保有权限。谁能准入、撤销、修改模型或处理争议，是任务架构的一部分。

### 3.2 三个容易混用的概念

**任务信任（mission trust）** 是依赖关系和使用决策：依赖方在当前情境下，是否让对象承担指定用途。**可信赖性（trustworthiness）** 是支持这种依赖的相关性质，例如身份、软件状态、链路可用性、来源、新鲜度和治理。**可信数据环境（trusted data environment）** 则是生成、传输、处理、共享和管理证据的整个社会技术环境。

因此，“建立了可信数据环境”并不等于环境里的每一份数据都适合任何任务。具体的依赖决策仍需成立。

### 3.3 怎样读正文的核心公式

正文将证据评估与依赖决策写为两个接口：

```text
T_o(t,c,m) = A(o, E_≤t, c, m; θ)
D_r,o(t,c,m) = π_r(T_o(t,c,m), C_t, m)
```

第一行问：截至决策时刻收到的证据，在给定假设下，对对象的指定任务相关性质支持到什么程度？第二行问：依赖方结合这一评估、权限、时限、错误后果及替代方案，允许、限制、推迟还是拒绝使用？

| 符号 | 含义 | 为什么需要保留 |
|---|---|---|
| `o` | 被评估对象 | 身份、设备、路径与数据产品不能混为一个分数。 |
| `t` | 决策时刻 | 证据和权限都会随时间变化。 |
| `c`、`m` | 情境、任务用途 | 同一证据对不同用途可能足够或不足。 |
| `E_≤t` | 此时已经收到的证据及其观测时间和来源 | 事后才到达的信息，不能假装决策当时已经知道。 |
| `A`、`θ` | 评估程序及其参数或假设 | 需要说明估计依据什么模型。 |
| `T_o` | 分主张的评估结果和不确定性 | 可以是状态、区间、意见或有定义的概率。 |
| `π_r`、`C_t` | 依赖方策略和当时约束 | 评估可信程度与授予使用权限分属不同问题。 |
| `D_r,o` | 具体依赖决策 | 将证据转化为有范围的行动。 |

正文没有把 `T_o` 固定为概率。若实现要输出概率，必须定义事件、模型和校准依据。0.9 的归一化声誉分数，不能直接解释为“任务有 90% 的成功概率”。相关基础来自主观逻辑、概率信任模型和 EigenTrust [51–53]；它们的输出语义并不相同。

### 3.4 四层主张怎样形成具体判断

观测有效性需要校准、环境、几何及物理互证；来源完整性需要版本、签名和处理关系；共享记录需要故障与治理假设；任务适用性需要当前时限、误差容忍度、用途和行动权限。

远程证明 [41] 支持对测量覆盖范围内的端点状态作出评估，NIST IoT 基线 [68] 给出设备能力背景，PROV [44、45] 描述记录的生成与派生关系。它们各自支持不同子主张。图 1 展示部署和信息方向，图 2 展示这些主张如何进入依赖决策；图 2 的箭头不代表前一层在逻辑上推出后一层。

本章给后续章节确立了评价单位：**一个有用途、有时间、有证据范围的主张。**

| 水下通信与安全 | 声学/光学条件、可靠采集、攻击和对策 | 延迟或丢包究竟意味着攻击、自然退化，还是暂时无法判断？ |
| IoT 信任与声誉 | 直接观测、推荐、上下文、更新和聚合方法 | 估计值代表哪种性质，能够支持何种使用？ |
| 来源、证明与零信任 | 数据派生、端点评估、资源访问策略 | 三种机制能否绑定到同一版本和同一决策时刻？ |
| 一般 IoT 区块链 | 存储、计算、通信、隐私和治理权衡 | 哪些信息适合共同记录，哪些保证要由链外机制提供？ |

这不是“某类文献缺几项、OAL 全部覆盖”的排名表。它的用途是找到可以组合的部分，并把组合前提显式写出来。

### 4.2 五个小节分别推进什么观点

**4.1 跨域协同与保证语义。** 协同控制文献研究不同平台怎样共同运动、搜索或跟踪，例如 3U 协同研究 [2]；海事无人搜索综述 [60] 提供感知、定位、通信与规划的应用背景。作者把控制输出进一步看作“有输入、模型、策略版本和预期用途的数据产品”。这里特别区分两种 consensus：控制中的一致性通常指状态收敛或协调；账本共识指在给定故障模型下对共享记录达成一致。二者的研究对象与保证条件不同。

**4.2 从攻击目录走向跨对象影响。** UAV 与水下网络综述 [16、18] 提供威胁分类，文章进一步追问：攻击一个网关，会怎样影响它承载的传输、转换、签名和下游产品？这使防护从“在节点上部署一种检测器”延伸到端点、密钥、转换及消费环节。与此同时，声学多径、噪声、环境衰减也能产生异常，故需要保留良性退化与证据不足的解释。

**4.3 为信任计算补上任务语义。** IoT 信任综述 [48–50]、水下决策树和隐马尔可夫研究 [78、79] 提供评估方法。作者要求每个输出附带对象、性质、上下文、来源、不确定性和允许用途。例如，“路由合作性高”与“传感器读数准确”是两个不同判断。将推荐写入账本，可以保存更新历史；推荐是否偏置、串谋或重复，仍要由评估机制处理。

**4.4 将来源、远程证明与授权对齐。** PROV [44、45] 描述怎么产生数据，RATS [41] 描述如何评估端点证据，零信任 [39] 组织资源访问决策。三者需要在同一任务产品和时间条件上连接，断联时还必须规定缓存评估与委托权限的有效范围。

**4.5 确定账本与物理证据的边界。** 区块链技术资料 [86]、IoT 集成研究和 UAV/海事认证方案，提供共识、合约、存储与身份架构。作者据此主张，账本部署位置必须与平台资源和任务主张对应。把复杂服务放到岸上或 USV 上可能可行，同时也会增加对这些服务节点的依赖。

### 4.3 最容易漏读的一点：来源不同不等于证据独立

同一 USV 可以为多个 UUV 提供推荐。即使被评估车辆不同，这些推荐仍可能共同依赖一套软件、时钟、定位、路径或管理者。因此，“推荐来自多个对象”不能自动变成“获得了多份独立互证”。这为第 6 章处理重复证据和共同原因埋下了伏笔。

本章的产出是一份**机制—问题对应关系**：既有研究提供组件，OAL 接下来负责给它们建立共同的说明格式。

<a id="chapter-5"></a>

## 第 5 章：The OAL Framework for Mission Trust——将要求写成可检查的结构

### 5.1 三个轴分别回答什么

OAL 的全称是 **Object–Assurance–Lifecycle**，即“对象—保证—生命周期”。它把三个问题分开：

1. **Object：评估什么对象？**
2. **Assurance：希望证明这个对象的什么性质？**
3. **Lifecycle：何时、在哪个任务阶段需要这项证明？**

三个轴在概念上可区分，但不同位置的证据和故障可能相关。图 3 的格子是需求和文献的定位坐标，格子覆盖率本身不构成有效性证明；不适用的组合也不必强行填充。

### 5.2 第一个轴：为什么恰好区分这四类对象

| 对象 | 这类对象承担什么含义 | 典型证据 | 重要区别 |
|---|---|---|---|
| 实体/行为主体 Entity | 能持有权限、承担责任或作出行为的主体，如组织、操作者、任务服务或自主代理 | 凭证、组织角色、授权委托、可问责行为 | 主体被授权，不说明其使用的设备未被攻陷。 |
| 平台/设备 Platform/Device | 执行任务的物理或虚拟端点，如无人艇、传感器、网关、计算模块 | 启动度量、配置、软件版本、自检、健康与能源状态 | 设备符合基准，也可能执行不适合当前任务的策略。 |
| 链路/路径 Link/Path | 包含介质、中继、安全关联和质量状态的动态端到端通路 | 时延、丢包、路由、认证状态、介质及网关信息 | 单跳正常不代表完整跨介质路径满足要求。 |
| 数据产品 Data Product | 有明确版本标识的观测、轨迹、模型、指令、告警、融合结果或审计材料 | 版本、签名、时间、来源、质量、校准与互证信息 | “逻辑上不可变的版本”是一种建模约定，真实存储仍需完整性核验。 |

这种分类使权限问题、运行状态问题、通信问题和产品问题不会被挤进同一个“节点信任分数”。同一无人系统可以在不同主张中扮演不同对象：作为被委托行动的主体时是 entity，作为被度量软硬件状态的端点时是 platform/device。

模型和策略也能纳入这四类对象：保存的模型文件是数据产品；部署该模型的执行实例属于设备评估范围；批准模型的组织是主体；模型分发途径属于路径。因此，治理服务和智能合约也需要接受评估。

### 5.3 第二个轴：四类保证分别使用什么文献

观测层吸收多传感器、多视图融合与物理观测研究，用于校准、几何、物理边界和交叉互证。但融合可能放大共同误差或被污染的输入，需要说明独立性假设。

来源层使用数字签名、内容标识和 W3C PROV [44、45]，并结合数据来源综述 [46、47] 与决策来源研究 [104]。其目的，是把输入版本、转换、责任主体、策略和输出绑定成可回查记录。对声明作出有效签名与声明本身准确，是两项不同主张。

账本层借用 Fabric 等共享状态机制 [105、106]，描述成员、背书、排序、验证、撤销和版本协调。治理规则是否合理、争议如何解决、提交内容是否符合物理事实，需要额外证据和程序。

任务层把新鲜度、相关性、不确定性、后果、政策和替代方案综合为依赖决策。这一层的关键是：产品评估结果需要与使用权限对接。

### 5.4 第三个轴：生命周期为什么必须延伸到恢复

表 4 将生命周期分成六个阶段。它强调安全不能在“成功接入”时结束。

| 阶段 | 核心检查 | 为什么前一阶段通过后还要继续检查 |
|---|---|---|
| 准入与认证 | 主体授权、端点状态、配置和最小权限 | 接入后，设备状态和权限可能变化。 |
| 感知与采集 | 时间、位置、校准、模态、观测质量 | 合法设备也可能产生不可靠观测。 |
| 传输与中继 | 路由、链路、安全关联、时延与交接 | 数据可能在途中变旧，或者经过新的依赖节点。 |
| 处理、融合与共享 | 输入、代码/模型、参数、策略与输出版本 | 转换会引入新的假设、偏差和责任关系。 |
| 决策与行动 | 当前用途、时效、不确定性、替代方案及安全回退 | 可共享的信息不一定可用于高后果行动。 |
| 审计、撤销与恢复 | 受影响对象、凭证和模型撤销、回滚、重新证明 | 修好一个设备后，其历史派生产品和已作出的决策仍可能需要复查。 |

断联尤其检验生命周期连续性。离线授权边界需要写明资源、允许动作、风险限制、证据年龄、到期条件和回退策略，还要有可依赖的时间与本地状态保护。执行先前获授的权限，与获得最新全局批准，是不同的授权依据。

### 5.5 用一个具体要求理解 OAL

以下是对正文结构的中文展开：假如要求“某目标位置产品可在下一次航线重规划时使用”，就不能仅填“已认证、已上链”。应分别检查：

- 哪个组织和服务有权提供或消费该产品；
- 采集与融合端点在相应活动时刻具有什么状态证据；
- 哪条路径影响了时延、内容与可用性；
- 使用的是哪个输入、模型与输出版本；
- 物理定位、来源、必要共享状态和当前任务适用性，各由什么证据支撑；
- 证据不足时由谁执行哪种限制或回退，事后如何复查。

正文建议为每个适用位置记录：对象/版本、所需性质、证据来源与覆盖范围、有效条件、接受规则、责任主体及缺失证据时的响应。OAL 的实际价值，就在于把含糊的“可信”拆成这类具体要求。

本章同时保留一个重要边界：未知或遗漏的依赖路径不会因为画了一个完整格子图就自动出现。第 6 章进一步处理已经识别出的对象关系和动态证据。

## 第 6 章：Evidence Dependencies, Threat Propagation, and Dynamic Reasoning——证据怎样进入决策

这一章是全文从静态分类走向操作过程的关键。它依次处理对象之间的关系、异常解释、证据更新流程、具体决策示例和可选择的推断方法。

### 6.1 依赖图表示什么，能够推出什么

正文使用随时间变化的有向多重图 `G_t = (V_t, E_t)`。节点对应四类对象，边有明确类型，例如主体控制设备、设备产生产品、路径传输产品、产品依赖输入、主体背书或消费产品。多重图允许同一对对象之间存在不同关系；时间、版本和状态区间则用于避免把不同时期的状态混在一起。

一个转换活动要绑定全部输入、输出、执行端点、责任主体、代码/模型版本及时间区间。PROV 的 activity 可以表达这种活动关系，但本文没有因此增加第五类 OAL 信任对象。

图首先支持**来源追踪、暴露分析和确定重新评估范围**。例如，某网关的软件状态受到质疑，所有经它处理的轨迹产品都值得重新检查。但“由这个网关处理过”不能直接推出“每条轨迹都错了”，也不能未经建模就沿图把所有分数下调。

若要作因果或概率推断，还需要条件关系、共同原因、参数和具体推断规则。图 4 因而把操作依赖与暴露标记区分开：红色虚线指向各自对应的对象，不表示一条已经得到证据支持的攻击因果链。

### 6.2 威胁分析如何从“攻击名称”变成“任务问题”

正文给出统一句式：具有能力 `C` 的攻击者作用于对象 `O`，经关系 `P` 影响任务结果 `I`，并在假设 `A` 下受到控制 `K` 的约束或检测。

其中最有用的变化，是要求把“初始对象—关系—任务后果”连起来。表 5 据此讨论凭证滥用、端点捕获或模型替换、路径操纵、数据污染、环境退化和证据缺失。每种情况同时列出控制措施及剩余的不确定性。例如，路径丢包可以触发减少依赖，但攻击者意图仍可能无法确定。

本章对异常的解释保留三个标签：

| 标签 | 指什么 | 对动作选择的含义 |
|---|---|---|
| Malicious，恶意 | 有证据支持对抗性或蓄意操纵的解释 | 可依据对象与风险采取隔离、撤销等有范围的响应。 |
| Benign-degraded，良性退化 | 有证据支持环境或运行退化的解释 | 可能需要降低使用强度、切换路径或补充观测。 |
| Unknown，未知 | 证据不足以解决当前解释或主张 | 可以限制或推迟使用，不必先认定设备恶意。 |

“未知”是对认知状态的描述，不是与攻击、环境退化并列的物理原因。恶意与环境退化也可能同时发生；正常运行和恢复状态另需表示。图 4 下方将“因果假设”和“证据状态”分开，正是在表达这一点。

### 6.3 CTG 的八步循环怎样理解

CTG 是 **Context–Temporal–Graph**：上下文、时间和关系图共同参与证据组织。它规定信息流程与应记录的内容，具体推断算法由实现者选择。

| 步骤 | 要做的事 | 防止哪类判断失真 |
|---|---|---|
| 1. 采集证据 | 记录来源、对象、观测与接收时间、时钟误差、上下文、值和来源关系 | 将迟到数据当成刚发生的观测，或丢失责任与版本关系。 |
| 2. 评估证据可靠性与依赖 | 区分自报告、外部验证和共用基础设施 | 把不同形式的报告视为同等强度证据。 |
| 3. 推断对象状态 | 用选定方法评估有名称的对象性质 | 得到一个含义不清的“总信任分”。 |
| 4. 检查依赖 | 找出下游待复查主张、共同原因与遗漏依赖 | 只看单节点而忽略共享定位或共享网关。 |
| 5. 表达不确定性 | 必要时修正评估，保留未知或区间 | 用单一肯定结论掩盖证据不足。 |
| 6. 作出策略动作 | 结合权限、时限、任务后果和替代方案决定使用范围 | 将“模型置信度高”直接当作行动授权。 |
| 7. 记录决策与版本 | 保存理由、策略、模型、评估及证据承诺 | 事后无法解释当时为何允许或限制行动。 |
| 8. 根据后续证据更新 | 通过独立评估的结果和后来验证修正证据库 | 将系统自己的决定当作真实标签，自我强化。 |

证据重复分为两种。完全相同的观测被多次转发时，同一次更新中只应计入一次；不同观测如果共享定位、标定、模型或环境，则应根据明确的依赖假设处理。随意给每条证据乘一个折扣系数，并不能普遍修正相关性。

### 6.4 逐步拆解原文的 USV 决策示例

这是构造性的策略示例，用来说明如何作出可审查的判断。**60 秒是示例中的策略阈值，不是本文验证得到的工程推荐值。**

任务是由 USV 网关判断某目标位置产品能否用于 UUV 航线重规划。策略版本 `p_7` 要求：授权委托尚未到期；产品来源核验通过；平台状态评估被接受；计入时钟误差后的观测年龄不超过 60 秒；具备不受已识别共同定位故障影响的互证。所有必要条件必须满足。

为突出新鲜度和依赖关系，示例先假定授权、来源和平台评估三项均通过。剩下三个产品如下：

| 产品 | 已知信息 | 应怎样解读 |
|---|---|---|
| `d_1` | 已签名观测；年龄区间为 `[42,48]` 秒 | 最坏年龄 48 秒仍不超过 60 秒，通过新鲜度要求。 |
| `d_2` | 融合产品，但唯一的观测父项是 `d_1` | 处理形式变了，观测信息仍来自同一条来源，不能新增一份独立互证。 |
| `d_3` | 来自第二个平台；年龄区间 `[58,66]` 秒；与 `d_1` 共用定位参考 | 最坏年龄达到 66 秒，无法满足示例的保守新鲜度上界；平台不同也没有解除共同定位疑点。 |

如果只看签名、平台数量或已记录条目数，可能误以为三份产品足够可靠。CTG 按具体主张检查后得到的结论是：**当前证据不足以支持这次航线重规划。** 系统应暂不执行该动作，启用 `p_7` 已授权的本地回退，并记录原因，无须把任何平台标成恶意。

以后，具有适当新鲜度且定位独立性得到合理支持的新观测，可以触发重新评估。单纯等待原有产品入账，不会使观测变新，也不会产生独立来源。

审计应保存的不只是“拒绝”这个结果，还包括逐项检查结果、来源标识、不确定性、策略和平台评估版本、委托依据及回退动作。这个例子集中体现了第 3 章的两个接口：先评估各项性质，再由策略决定是否使用。

### 6.5 本章怎样使用信任计算文献

表 6 将方法视为可填入 CTG 的不同实现候选：加权多属性评分便于解释；概率方法适合有模型的序贯更新；主观逻辑显式表示相信、不相信及不确定性；状态空间或马尔可夫方法描述状态延续与恢复；规则、树和模糊方法组合异构信息；机器学习处理非线性模式；图方法检查关系及影响范围。它们分别需要权重、先验、状态定义、训练数据或关系假设的支持。

本章对水下研究的讨论尤其具体。隐马尔可夫研究 [79] 用丢包率和误包率映射潜在状态，其 MATLAB 示例使用十个观测及随机初始化概率，支持的是一种时间状态建模展示。TEUC 研究 [78] 结合数据、链路、节点证据与 C4.5 树，并在初始部署无攻击、初始训练证据未污染的设定下评估。水下信任设计综述 [80] 则区分证据收集、评价、传播和更新。

这些文献支持作者提出实现要求：分开节点行为和传感器真实性，同时评价攻击分类与任务损失，并保留良性退化的可能。EigenTrust [53] 的相对声誉、主观逻辑 [51] 的意见和概率模型 [52] 的概率解释也应各按本来含义使用。

本章最终交付的是一套**可记录、可解释的决策过程**。具体阈值、概率校准、回退安全性和性能收益，还要在实现研究中确定。

<a id="chapter-7"></a>

## 第 7 章：Blockchain-Assisted Assurance: Roles and Boundaries——账本应放在什么位置

### 7.1 先确定治理需要，再决定是否使用账本

正文提出的候选条件是：**多个独立管理的参与方，需要共同控制被接受的状态转换，而且无法把这一职责交给共同认可的单一保管方。** 多组织参与、已经使用签名或经常断联，单独都不能充分说明必须使用区块链。

选型必须说明：要阻止谁作出什么单方面修改，谁能批准冲突更新，能容忍怎样的故障，要求多大可用性，再比较实现成本。应纳入的替代方案包括受保护审计记录的认证数据库、独立见证的签名追加日志，以及共同管理的复制数据库。

Fabric [105、106] 是代表性实现参考，而非本文规定的唯一平台。成员准入方式与共识资源成本需要分别考虑；许可成员身份不自动提供拜占庭容错，无许可参与也不等同于必须使用工作量证明。

另一个具体区别是 Fabric 的执行/背书、排序和验证：进入区块的交易未必通过应用验证并更新了状态，因此依赖方应核验有效提交。对 Raft 配置的解释也必须限定为其故障模型，不能因为采用许可链就认为排序节点的任意恶意行为都能被容忍。

### 7.2 链上与链外分别保存什么

大体积、敏感或高频内容，如视频、声呐、点云、详细证明证据和精细位置，主要保留在受访问策略控制的加密链外存储。链上保存较小的可核验引用和状态：内容标识或 Merkle 根、生产者/保管者、时间范围、策略与模型版本、证明结果承诺、背书、撤销和审计结果。

承诺必须说明覆盖的是哪些确切字节或规范化表示、使用什么算法，以及针对明文还是密文。否则，不同组件可能以为验证了同一产品，实际覆盖的内容却不同。

本节利用 IoT 区块链、隐私和海事治理文献，明确三个互不等价的性质：

- **完整性：** 能否发现已承诺内容与当前内容不一致。
- **可用性：** 获授权的人是否仍能取得内容；只有摘要并不能恢复丢失文件。
- **隐私：** 谁可以看到内容及其关联；哈希仍可能泄露相等关系，或让可预测内容遭到猜测。

删除链外文件后，链上元数据也可能继续暴露身份、时间与关联。因此，隐私需要加密、最小化、选择性披露和保留规则共同设计。

### 7.3 五种设计模式分别支持哪种主张

| 模式 | 账本主要记录什么 | 支持的主张 | 需要补充的证据 |
|---|---|---|---|
| 成员与权限登记 | 组织、角色、凭证状态、委托与撤销版本 | 多方对身份和策略状态的一致认识 | 主体真实意图、端点安全、紧急权限冲突处理。 |
| 远程证明锚定 | 证据摘要、验证者、结果、参考值与策略版本 | 端点评估历史可问责、可复查 | 测量覆盖、验证者可信程度、未测量的运行状态及物理观测。 |
| 来源承诺 | 数据版本、转换与交接关系、输入根和背书 | 被记录来源与处理过程的篡改可发现性 | 捕获是否完整、模型是否偏置、输出是否符合语义及隐私要求。 |
| 考虑分区的审计与对账 | 序号范围、批次根、本地策略/模型版本及重连事件 | 相对保留检查点发现部分缺口或历史冲突 | 未捕获事件、无见证尾部删除、事件时间和物理事实。 |
| 策略与模型协调 | 获批版本、激活/回滚时间、批准者 | 已同步成员对批准版本的一致认识 | 各端点是否实际安装、离线成员状态，以及版本自身的安全和准确性。 |

这五种模式来自 UAV/IoT 认证、远程证明、来源系统与许可账本研究的综合。原论文提供局部机制，作者把它们映射为跨域任务中的使用模式。

### 7.4 怎样从原型研究中读出“支持范围”

Tan 等的 UAV 认证方案 [28] 在模拟的 `10 km × 10 km` 任务、云端 Fabric 节点和基站覆盖假设下评估相关操作与开销。SwarmAuth [31] 结合 PUF 互认证、账本注册与位置相关聚类，使用 EVM 实现和仿真分析安全特性与开销。它们能够支持认证、成员登记和相关原型配置的讨论；迁移至水下分区、多组织治理和任务决策，需要增加相应验证。

远程证明研究 [43] 的例子进一步说明为什么配置不可省略：互证明 TLS 在同一主机的 SEV-SNP 虚拟机上报告 31.2 ms，在所测 Intel 固件 TPM 上报告 476.1 ms；ARM PSA 设备当时未实现 TLS，因而没有该握手时延测量。本文引用这些结果是为了说明异构证明具有平台相关成本，不能把它们当成跨域网络的一般通信时延。

证明结果的允许使用年龄也是策略条件。一个端点刚通过评估，随后状态仍可能变化；结果未到期不表示设备状态期间绝不改变。

### 7.5 断联、对账和 CAP：哪些保证还能成立

断联节点可保留已签名、哈希相连的本地序列，重连后提交批次根、序号范围和先前检查点。验证方检查签名、成员信息、连续性、重复项和版本。在有独立检查点、受保护计数器或收据等支持时，部分遗漏或冲突可以被发现。

但“某条记录在已承诺批次内”只说明批次成员关系。未进入记录的物理事件，以及从未被独立见证的末尾记录删除，可能仍无法识别。这里区分的是**记录完整性**与**捕获完整性**。

本章借助 CAP 基础分析 [118]，将三个问题分开：账本安全性关注正确副本是否确认冲突历史；活性关注在协议要求的通信和法定数量条件下，请求能否推进；本地任务权限关注断联设备此时允许做什么。失去共识所需条件可以暂停新提交，而不必让所有本地功能停止。

CAP 中的可用性条件也不是任务的硬实时期限保证。需要最新全局状态的离线决策，必须等待、依据显式减弱的状态假设运行，或执行已授权回退；本地已委托动作可在其边界内继续。后来达成一致，只能补充审计与冲突处置，无法改变已经发生的物理后果。

### 7.6 撤销为何必须同时考虑“事件何时发生”和“何时得知”

原文给出时间例子：凭证于 12:00 生效撤销，断联 UUV 在 11:55 行动，网关于 12:30 得知撤销。对这次行动的解释，要结合撤销生效规则、行动时间的可信区间、当时已知权限及委托条件。

如果时间区间与撤销时点重叠，或怀疑密钥早已被窃取，结论可能仍有争议。一条签名时间戳本身不能消除这些问题。恢复时还应检查受影响模型、数据产品、来源后继和历史任务决策，而不仅是重新启用设备。

### 7.7 本章最后的架构判断

稳定控制、避碰和紧急机动应有适合本地时限的控制与安全论证。账本可以在操作前协调版本，在较慢时间尺度支持监督和跨方授权，在事后支持审计。解除实时控制对共识进度的依赖之后，本地感知和回退本身仍需验证。

因此，图 6 的左右两组——账本支持的记录与补充控制——必须一起读。**账本的价值要由共同治理需求、实现假设和与替代方案的比较来证明。**

<a id="chapter-8"></a>

## 第 8 章：Evaluation Practices and Evidence Maturity——什么证据支持什么结论

### 8.1 六类证据画像如何读

本章将“提出了一个方案”“实现了一个组件”“在真实场景运行过”等不同形式分开。图 7 的 L0–L5 编号用于组织证据，不能当作从低到高的严谨性总分。

| 类别 | 中英文名称 | 可以说明什么 | 还要另外记录什么 |
|---|---|---|---|
| L0 | 概念论证 Conceptual Argument | 用例、分类、架构与设计理由 | 假设是否清楚，推理是否可追踪。 |
| L1 | 分析性证据 Analytical Evidence | 指定性质在明确模型、攻击者和系统假设下的分析 | 分析对象、范围、假设与结论形式。 |
| L2 | 仿真或数据 Simulation or Data | 指定仿真模型或记录数据上的表现 | 数据来源、代表性、模型适配和实验条件。 |
| L3 | 原型或试验台 Prototype or Testbed | 实现与接口在具体配置和负载下的行为 | 软件、硬件、拓扑、工作负载及测量范围。 |
| L4 | 实地试验 Field Trial | 特定真实物理环境下的运行与集成 | 涉及哪些平台、链路、条件及参与方。 |
| L5 | 持续运行 Sustained Operation | 持续多方运行、变化、故障、审计和恢复经验 | 时长、组织变化、凭证轮换及实际经历的事件。 |

一个实地试验不必包含形式化证明，一份形式化分析也不因此缺乏严谨性。某个系统可以同时拥有 L1、L2、L3 的不同主张证据。单个账本组件的吞吐量测试，不能给整个任务系统自动授予某个等级。需要分别判断严谨性、环境代表性、系统范围和持续时间。

### 8.2 本章综述的评价资源各有何用

| 文献或资源 | 在本文中被用于说明什么 | 迁移至跨域任务仍需补充什么 |
|---|---|---|
| TON_IoT、Edge-IIoTset、CICIoT2023 [119–121] | 网络、主机、设备遥测及攻击数据，可用于异常推断实验 | 海事拓扑、自然退化、跨介质通信与任务后果模型。 |
| SeaDronesSee [122] | 海事无人机图像与元数据，支持检测和跟踪实验 | 指定的物理主张、相应真实参照及其他观测域。 |
| GNSS 欺骗研究 [65] | 合成操纵信号训练、两个真实欺骗/转发欺骗数据集验证 | 新平台、条件及任务用途下的适用性。 |
| AirSim [123] | 空中平台的物理、传感、视觉与部分硬件在环能力 | 水声链路、治理、证明、来源及任务损失等模块。 |
| UUV Simulator [124] | 水动力、推进器、传感器及多机器人水下仿真 | 对所用水动力与传感模型的实地验证。 |
| Aqua-Sim NG [125] | 水下网络协议、路径、时延、丢包及分区实验 | 物理观测有效性和任务层含义。 |
| 许可账本试验台与跨域演练 | 提交、资源、成员变更、故障恢复与集成运行 | 代表性证据负载、场景覆盖和可重复的评估设计。 |

作者提出可以组合这些组件，但它们尚未在本文中组成一个已验证的联合实验平台。连接模拟器还涉及版本、时间同步、共享几何、接口和事件交换的验证；工具接通本身不会产生任务真值。

### 8.3 为什么准确率和吞吐量不够

正文要求五组指标共同评估：

1. **推断质量：** 分类、概率校准或区间覆盖、缺失证据下的不确定性、检测与恢复延迟、分布变化下的表现。
2. **任务效果：** 完成率、耗时、覆盖、违反安全约束的情况、决策损失以及资源配置结果。
3. **网络与资源成本：** 每次证据事件字节量、时延分布、能源、存储增长、占空比和分区时长。
4. **账本行为：** 背书和最终确认时延、真实批处理条件下的吞吐、成员变更、服务中断、对账和争议历史。
5. **可问责性：** 决策来源能否解析、查出受影响产品需要多久、版本是否可追溯、撤销和恢复是否成功。

一个总体准确率较高的检测器，如果偶尔错误隔离唯一中继，仍可能带来较大任务损失。类似地，只统计成功送达消息的平均时延，会漏掉超时或完全未送达的事件。本章的重点是把错误类型及其后果一起计量。

### 8.4 公平比较需要怎样设计

实验要同时跨越对象、威胁和情境：被攻陷主体与设备、单节点与串谋、干扰与自然衰落、新鲜与陈旧证明、独立与相关传感器、短期与长期分区，以及不同后果等级的策略。

训练、阈值选择、校准和最终评估要分开，数据划分应防止同一采集过程、平台、地点或时间段的信息泄漏。统计不确定性宜依据独立任务或仿真运行，不能把同一任务中的相关数据包当成大量独立重复试验。

基线应包括认证数据库、签名日志以及独立见证或复制日志；消融分别去掉持续评估、来源、依赖处理、不确定性或复制等功能。比较双方应获得相同证据、任务负载、资源、攻击能力和相当调参预算，并写明各自达到的保证及其信任假设。

### 8.5 本章表达的观点

评价要围绕**具体主张的证据需求**，并测量该主张失效时的任务代价。补充材料中的 16 条详细编码是工作流程记录，不是整个领域只有这些研究有有效证据，也不是成熟度统计。本章提供后续评价蓝图，没有报告 OAL 的集成性能优势。

## 第 9 章：Discussion and Research Agenda——怎样把框架转化为可检验的工作

本章将前面的分类、依赖和技术边界提升为设计原则，再给出六项研究命题、保证论证的方法及 CDUTP 路线。它不是新增一轮平行的技术综述，而是使用已有文献和前文推理提出下一步研究。

### 9.1 三个理论含义

第一，主张可以在明确推断规则和共享假设后沿类型化依赖组织起来。但 OAL 分类本身不提供“组件分别正确，所以系统一定正确”的组合定理。

第二，信任有用途边界。同一份证据可以支持低敏感信息共享，却不足以支持协同导航；用途变化意味着保证要求变化。

第三，不确定性要进入运行策略。“未知”需要映射为可记录的限制、推迟、互证或其他动作，不能仅在界面上显示一个模糊分数。

作者用四句话区分论证对象：来源论证历史，观测论证外部世界，账本论证共享记录，任务适用性论证使用后果。决策来源与 AI 来源文献 [104、116] 提供可追溯性的基础，OAL 补上特定使用者的任务判断。

### 9.2 分区、韧性和多样性

断联应被视为需要设计的常态工作模式。重连后的工作包括同步状态和解释语义：行动时本地知道什么策略，撤销何时生效，哪些主张因新信息需要复评，以及观测冲突是否影响任务结果。

本章进一步区分**架构冗余**与**证据独立性**。增加设备实例可以提供替代容量，但共用时间源、管理员、定位、模型或网关仍可能形成共同故障。图上的高中心性可以提示一个节点影响很多路径，却不能单独计算其失效概率或任务损失。

这一点也不应被反向简化：不同来源的端到端签名观测经过同一个网关，并不意味着其来源信息必然完全相同。它们共享传输与可用性依赖；网关是否还能改变、筛选或偏置解释，要看其具体处理角色和保护机制。

### 9.3 治理、隐私与人的权限

海事区块链采用和治理研究 [32、34] 提供组织与政策背景。作者将治理作为安全机制的一部分：谁批准验证者、参考值、合约、模型、紧急权限和恢复结果？如果错误参考值让被攻陷设备看起来符合要求，治理问题就会进入技术判断。

隐私也包括跨任务标识、时间、路径交接和模型使用记录可能暴露的活动关系。可问责假名性是一种候选设计：日常验证可以确认某授权角色作出行为，身份解析则需要受治理的事件处理程序。

高后果恢复与争议处理可能需要人类审查。审查应保留模型输出、理由、策略版本、不确定性、替代选项及后果；人工覆盖同样要有明确授权和可追溯记录。

### 9.4 六项研究命题逐一解释

这些命题是未来比较研究的假设，并非本文已经得到的结果。每项都要预先定义任务分布、威胁模型、实现、主要指标和有实际意义的效果门槛。

**P1：分开保证主张，是否减少不安全接受？**

比较保留四类独立评估结果的实现与单一总分实现。在存在“签名正确但物理无效”观测的相同场景下，双方获得相同原始证据、动作集合和调参预算，并在匹配的错误隔离代价下比较不安全接受率。目标是检验分开主张是否改善决策，而不是让某一方拥有更多传感器或随意采取更保守的策略。

**P2：显式建模共同原因，是否改善概率校准？**

比较处理共享传感器/推荐者原因的概率实现，与把相关证据当作条件独立的消融版本。要定义二元事件和预测时间范围，分别拟合参数，在留出数据上使用预先确定的校准指标、Brier 分数等评分规则及决策损失。应改变相关性强度和来源完整度，查看在哪些条件下有效。该命题只适用于有明确概率语义的输出。

**P3：区分因果解释并允许未知，是否降低任务损失？**

在正常运行、环境退化、攻击和证据中断混合的条件下，比较保留多种解释及未知结果的实现与可信/不可信二分实现。双方应拥有相同证据和行动权限。需要分别去掉因果诊断、去掉拒绝判断能力，以区分“解释更好”与“只是多了一个保守动作”的收益。损失要同时计入补充互证的延迟、错误隔离、不安全接受和可用性损失。

**P4：有边界的离线授权，能否取得更合适的可用性与权限风险权衡？**

同时比较要求最新全局批准、有边界离线授权、无约束离线自主三种方式。指标包括期限前完成的获准任务，以及与生效全局策略冲突的动作。改变离线权限的范围和持续时间，报告权衡曲线及资源成本。事件当时本地委托是否有效、事后发现是否与全局状态冲突，要分别判断。

**P5：账本的审计收益，是否确实需要账本架构？**

在指定故障模型下引入管理员展示不一致历史或扣留记录的情况，比较独立验证者维护的许可账本与单管理员签名日志。衡量已接受测试事件的恢复比例、不一致视图检测和达成可核验历史的时间，并使用独立事件记录作为参照。还要加入独立见证或复制日志基线，判断收益来自账本，还是任何合理的共同见证机制都能提供。通信和错过期限的成本另外报告。

**P6：多维评价能否选出任务表现更好的配置？**

从同一批候选配置中选择系统：一组只按交易和网络指标选择，另一组还考虑观测、端点、治理与任务结果。使用相等评价预算和固定选择规则，再在配对的独立留出场景中比较任务损失。这个命题检验的是“评价维度能否改善选型”，而非预先断言某种算法必定最佳。

六项命题形成一个可检验链条：分别考察主张结构、依赖建模、不确定性、离线权限、账本价值和评价标准。需要报告效果大小、不确定区间、零效果及不利结果；某一实现成功只能支持其已测试范围。

### 9.5 从 OAL 格子走向保证论证

**Assurance case，保证论证**，是把有范围的主张、推理依据和支持证据组织起来。正文示例将顶层主张限定为：“融合产品 `d_17` 在天气类别 `w`、策略 `p` 下，适合消费者 `r` 在时刻 `t` 之前用于航线重规划。”

往下展开，分别要求：观测的传感器、校准、几何和互证依据；输入版本、生产者、转换、交接和时间；需要共享状态时的成员、背书、排序及策略版本；以及新鲜度、不确定性与具体动作后果之间的联系。

这里又区分两类不同问题：**evidence gap，证据缺口**，是缺少必要支持；**potential defeater，潜在反驳因素**，是出现反证或关键假设受到挑战。两者都可能使动作受限，但不能用同一个“证据少”概括。

保证论证也应包含活动时刻。网关接收数据时证明尚新鲜，稍后转换并背书时已经过时，后一个活动仍需连续性假设或新证据。恢复时可以做有范围的处理：隔离有疑点的派生轨迹，同时保留仍有独立支持的原始观测；限制网关背书权限，同时在条件允许时保留紧急中继功能。

评价这种结构本身，还可以测量关键证据缺口、无效论证识别、查找受影响产品所需时间，以及争议处理过程。总体覆盖比例不能掩盖一个关键安全条件缺失。

### 9.6 CDUTP 究竟想标准化什么

CDUTP 是 **Cross-Domain Unmanned Trust Profile，跨域无人系统信任配置规范提案**。这里的 profile 指一组共同语义、字段和绑定规则，不是设备信誉档案。

它拟复用已有基础：零信任 [39] 的资源和请求中心策略；RATS [41] 的证明角色；PROV [44、45] 的派生关系；NIST 设备基线 [68]；3GPP UAS 与海事服务规范 [139、140]；以及 SUIT 安全更新架构 [141]。这些文献承担不同角色，引用它们本身不能证明接口互通。

一个配置实例至少应说明对象和类型、主张及保证层、签发者与依赖角色、证据引用、观测/签发/到期时间、情境与允许用途、不确定性或评估结果、策略/模型/模式/合约版本、隐私标签、父依赖、撤销引用及链上链外绑定。

共同语义比强制采用一种报文编码更重要。例如，水声链路可以使用紧凑编码，但“观测时间”不能在另一组件中被解释为“接收时间”。正文建议先明确用例与主张范围，再定义词汇和符合性测试，组织独立实现互通测试，评估多组织隐私治理，之后推进标准衔接。当前提案仍没有规范性 schema、实现或完整测试套件。

### 9.7 本章的实质观点

框架的价值应通过反例、对照和任务损失来检验。设计应从依赖决策出发，保留证据身份、共同原因、时间和权限，把版本化政策及治理材料也作为需要评估的对象。后续研究的目标是证明这种结构在具体条件下帮助人或系统作出更合适的判断。

## 第 10 章：Limitations of the Review and Framework——结论在哪些范围内成立

本章不再引入新的机制综述，而是将全文的证据与推断边界集中说明。它是读懂贡献性质的必要部分。

### 10.1 文献综合的边界

英文语料、有限发现窗口、相关性检索、取得全文的情况和作者判断，都会影响选入的资料。现有记录可以追踪选择与分析范围，但不能据此估计整个领域的方法比例或汇总有效性。详细编码只覆盖选定比较，也没有报告独立重复编码与编码者一致性估计。

因此，代表性机制比较与整个领域分布统计，是不同证据任务。第 2 章的方法、第 4 章的描述表和第 8 章的证据画像，应在这个一致边界下阅读。

### 10.2 跨域迁移与实现的边界

许多机制来自 UAV、IoT、车联网、工业来源系统和企业账本。它们面对的威胁分布、能源、时延、连通性和治理可能不同。本文提出迁移时要检查的条件，没有测量迁移收益。

OAL、关系集合、CTG、证据画像、研究命题和 CDUTP 属于作者的概念架构。本文没有新增集成实现、形式化组合证明或任务实验，因此没有给出整体安全性、校准、可用性和审计性能改善的实测结论。

实际图系统还需要抽象粒度、相关性、隐私、到期、循环、冲突主张及计算通信成本的规则。概率实现另需事件和预测范围、模型与校准证据。

### 10.3 本章如何帮助判断文章价值

文章目前能够提供的是：一套组织问题、说明假设、连接机制和安排验证的结构。它是否覆盖足够多场景、是否便于一致应用、是否比替代方法更有效，需要后续评估。把这些待验证项读清楚，才能准确使用第 9 章的命题和研究路线。

<a id="chapter-11"></a>

## 第 11 章：Conclusions——全文最终落在哪个判断上

本章没有引入新的文献群，而是收束前面的证据与作者综合，形成四个结论。

第一，空中—水面—水下协同使信任成为从物理观测延伸到任务使用的端到端问题。OAL 用四类对象、四类保证和完整生命周期组织它。

第二，依赖图与 CTG 帮助表达证据流、共同原因、未知状态、策略和审计，保留数值输出的明确语义。

第三，在多组织需要共同状态控制时，区块链是候选协调机制；其价值受治理、故障与成本条件约束，并需要与签名日志和复制数据库比较。物理互证、端点评估、本地安全、隐私和治理仍提供各自的保证。

第四，CDUTP 和六项命题给出后续互操作与验证方向。下一步应联合形式化分析、受控实验、实地证据与治理演练，测量决策后果及支持决策的证据质量。

**全文希望形成的实践是：每次重要的任务使用，都能够追溯到当时有效、范围清楚、证据充分程度可说明的保证，以及明确保留下来的不确定性。**

| Corroboration / Evidence Deduplication | 互证 / 证据去重 | 互证需要有根据的独立支持；去重防止同一观测经转发、融合或推荐后被反复计数。去重之后仍需处理相关性。 |
| Malicious / Benign-Degraded / Unknown | 恶意 / 良性退化 / 未知 | 前两者属于有支持的原因解释，后者表示证据不足。原因可共存，未知不等于恶意，也不等于正常。 |
| Epistemic Uncertainty | 认知性不确定性 | 由于证据或知识不足，当前主张无法充分确定。本文要求把这种不足保留下来并映射为运行策略。 |
| Calibration / Subjective Logic / Reputation | 校准 / 主观逻辑 / 声誉 | 概率校准关心所报概率是否与事件频率相符；主观逻辑显式表示意见与不确定性；声誉可能只是相对排序。三者的数值不可直接互换。 |
| Brier Score | Brier 分数 | 二元事件中，预测概率与实际 0/1 结果之差的平方取平均。P2 用它配合校准指标和决策损失评价概率输出；它不评价一般声誉分数是否“可信”。 |
| False Isolation / Unsafe Acceptance | 错误隔离 / 不安全接受 | 将正常或仍有用对象错误隔离，以及将不适用产品用于有后果的任务。本文要求同时考虑两类错误的代价。 |
| Abstention / Decision Loss | 暂不判断 / 决策损失 | 证据不足时不强行分类或使用；同时记录因此产生的延迟、可用性损失和其他任务后果。保守动作也有成本。 |

### 5. 账本与治理：同一术语不能扩大保证范围

| English | 中文 | 在本文中的准确含义与阅读要点 |
|---|---|---|
| Permissioned Ledger | 许可账本 | 参与和角色受明确准入规则管理的共享账本。成员受控不代表没有内部恶意，也不自动决定共识算法。 |
| Consensus | 共识 / 一致性 | 账本语境关注共享记录状态的协议一致；协同控制语境关注代理状态收敛或协调。应先识别语境。 |
| Endorsement / Ordering / Valid Commit | 背书 / 排序 / 有效提交 | 在代表性 Fabric 架构中承担不同步骤。交易入块后可能被判无效；需要核验是否通过验证并形成有效状态更新。 |
| Finality / Safety / Liveness | 最终确认性 / 安全性 / 活性 | 在本文账本语境中，分别涉及确认结果、避免正确副本确认冲突历史，以及满足协议条件时请求能够推进。账本安全性不等于车辆物理安全。 |
| Crash Fault Tolerance / Byzantine Fault Tolerance | 崩溃容错 / 拜占庭容错 | 前者处理相应停止或崩溃故障模型；后者处理更广的任意偏离协议行为，保证均有协议假设。许可成员和拜占庭容错是不同属性。 |
| Quorum | 法定数量 / 协议所需参与条件 | 协议推进所要求的参与数量或集合条件。失去条件可能阻止新提交，不意味着本地全部功能都必须停止。 |
| Witnessed Signed Log | 经独立见证的签名日志 | 用签名与独立持有的见证/检查点支持日志核验，是评估账本审计增益时的重要替代基线。 |
| Merkle Root / Inclusion Proof | Merkle 树根 / 包含证明 | 将一批内容绑定至根，并证明某项属于该批内容。包含证明不能证明现实中所有事件均已进入批次。 |
| CAP Result | CAP 不可能性结果 | 本文引用的是任意分区下，线性一致的共享读写状态与非故障节点每次请求完成要求不能同时得到保证的基础结果；它不是硬实时性能承诺。 |

### 6. 生命周期、评价与互操作

| English | 中文 | 在本文中的准确含义与阅读要点 |
|---|---|---|
| Bounded Offline Authorization / Local Authorization Envelope | 有边界的离线授权 / 本地授权边界 | 预先限定资源、动作、风险、证据年龄、到期和回退；需要相应时间及本地状态保护。 |
| Revocation-Effective Time | 撤销生效时间 | 权限撤销何时起作用，与参与方何时收到撤销通知不同。审计需结合可信事件时间和当时可知状态。 |
| Reconciliation / Recovery | 对账与冲突协调 / 恢复 | 重连后核验序列、版本和冲突，复查受影响主张并形成有依据的恢复范围；后来的记录一致不能改变既有物理后果。 |
| Fallback / Graceful Degradation | 回退 / 渐进降级 | 在缺少某些条件时执行预授权替代动作或降低能力。回退方案的安全性也必须结合任务环境验证。 |
| Claim-Specific Evidence Profile | 面向具体主张的证据画像 | 用 L0–L5 记录分析、仿真、原型、实地与持续运行等证据形式，同时保留范围与条件；不是单维总等级。 |
| Ablation / Distribution Shift | 消融 / 分布变化 | 消融单独移除一个机制以辨识贡献；分布变化关注新环境与训练/校准条件不同时的表现。 |
| Cross-Domain Unmanned Trust Profile (CDUTP) | 跨域无人系统信任配置规范提案 | 拟统一共享主张、证据引用、版本、时间、权限和依赖语义。是作者研究议程，尚非已完成标准。 |
| Conformance / Interoperability | 符合性 / 互操作性 | 前者检查实现是否遵循明确规则，后者检查独立组件能否共同工作。共同引用某个标准并不自动建立二者。 |

### 3. 三条阅读路径

**先抓住核心问题：** 阅读本导读第一部分，再看第 3 章的两个接口和四类主张，接着完整读第 6 章的三个产品示例。能解释为什么“签名、入账、多平台来源都存在”仍可能不允许重规划，就已抓住文章主线。

**准备讨论方法贡献：** 连读第 4、5、6、9、10 章。关注文献机制与作者整合的区别、OAL 如何变成保证论证，以及需要怎样的实验证明这种结构有用。

**准备实现或设计实验：** 连读第 5 章的需求字段、第 6 章的证据循环、第 7 章的架构条件、第 8 章的实验设计和第 9 章的 P1–P6。由此写出具体对象、主张、证据、时间、策略、替代方案和评价指标。

### 4. 用六个问题检验自己是否真正理解

1. 一份错误观测能够同时满足签名、来源和账本一致性吗？如果能，缺少哪种支持？
2. 同一观测被转发、融合、重新签名后，为什么不必然增加独立证据？
3. 为什么可以限制一个对象的用途，却不认定它恶意？
4. 为什么多组织参与和长期断联，都不能单独证明需要区块链？
5. 为什么一个有实地运行经验的系统，仍可能没有某项性质的形式化证据？
6. 如何设计对照，检验 OAL/CTG 的收益确实来自主张与依赖结构，而非更多证据、更大预算或更保守权限？

相应答案分别位于第 3、6、7、8、9 章。能将这些区别应用到一个具体任务，意味着读者已理解文章的分析方式，而不只是记住了章节名称。
