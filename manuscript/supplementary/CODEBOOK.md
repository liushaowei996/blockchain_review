# OAL extraction and reproducibility

The analytical sample contains 39 purposively selected original mechanism studies and 89 claim records. Nineteen target UAV (11), maritime AIS (3) or underwater (5) applications; twenty supply transferable mechanisms. Application domain and evaluation setting are separate fields. The bibliography contains 123 references: the 39 coded studies and 84 contextual/methodological/evaluation references. `current-reference-roles.csv` identifies every role, and `oal-study-register.csv` gives source versions, strata and retrieval links. `original-citation-disposition.csv` records all 141 original references. The expansion revisited 14 previously uncoded original candidates, adding four; ten remain incompletely accessible. `expansion-screening.csv` records the targeted checks. This is a structured narrative sample, not a census. Full texts are retained privately and are not distributed.

`oal-study-mapping.csv` is the manually prepared analytical input. Each row contains a study identifier, stable bibliography key, domain, scoped mechanism claim, one object, one assurance layer, the lifecycle stages supported by that claim, the reported evidence profile, and a passage locator. The profile describes the method and setting supporting the named mechanism. It does not validate every surrounding architectural claim or imply integrated maritime assurance.

Objects: E entity/principal; P executing platform/device; L link/path; D versioned data product. Layers: O observation validity; C commitment/provenance integrity; G shared ledger/governance consistency; M mission-use suitability. Stages: A admission; S sensing; T transmission; F processing/fusion/sharing; D decision/action; R audit/revocation/recovery. D has a different meaning on the object and lifecycle axes.

L0 = concept/architecture; L1 = mathematical, formal or security analysis; L2 = simulation or recorded-data evaluation; L3 = implemented prototype/testbed; L4 = operating trial with specified physical conditions; L5 = sustained multi-party operation with duration and governance history. These are complementary forms, not quality ranks. Multiple forms may be assigned. No blanket L4 is assigned merely because hardware or a recorded field dataset was used.

The heatmap expands only the lifecycle list within each claim row, then counts distinct study IDs per exact object/layer/stage cell. It never crosses unrelated object, layer and stage labels. It has 96 possible cells and 25 nonempty cells in this sample. Counts overlap and cannot be summed to obtain a study count. A zero means no coded claim, without deciding whether that cell is applicable to every mission or absent from the field.

Coding uses one extraction process checked against source passages and aggregation rules; no independent duplicate coding or inter-rater agreement is claimed. Some cited full texts are author manuscripts, with locations given by their PDF pagination. The ARCADIAN-IoT stable key retains `2022` although its chapter is cited by the 2023 print/copyright year. The digital-twin paper uses the available author-manuscript version. Interpretation of ambiguous deployment descriptions is deliberately narrow and documented in the scope column.

Reproduce the numerical outputs with Python 3.10 or later and `cryptography`:

```
python supplementary/replay_case.py
python supplementary/build_figures.py --data-only
python supplementary/analyze_oal.py
```

Run from the manuscript directory or use absolute script paths. The replay regenerates the CSV/JSON results and verifies signatures, tamper rejection, Merkle branches, arrival-order invariance and duplicate handling, signer subsets, the local-authority example, and serialization accounting. The public deterministic keys are test fixtures. Consensus and Fabric are not executed; latency sensitivity inputs are assumptions. ML-DSA is included only through standardized signature-length arithmetic.

The editable artwork is supplied in `figures/Figures-revised.vsdx`, with one page per figure. The original Visio layout, colors and diagram geometry are retained where they convey the same content. Figure 3 pairs the OAL framework schematic with a heatmap whose cell values follow `oal-cell-counts.csv`; `mapping-summary.json` exposes its aggregate counts. All 96 displayed cells have been checked against the claim CSV. After changing the coding, regenerate the numerical outputs, then run `supplementary/update_oal_visio.ps1` on Windows with Visio to update the native Figure 3 cells, headings and profiles and export that page. The other six figure PDFs are preserved by this targeted update.

To export the seven figure pages, run `python supplementary/build_figures.py` on Windows with Microsoft Visio installed, or run `supplementary/export_visio_figures.ps1` directly. The export script opens the drawing read-only and produces PDFs with selectable vector text and diagram geometry. Figure 2 retains the original raster lighthouse illustration; Figures 1 and 3–7 contain no raster images. Figure 7 uses six color-coded panels of native text boxes and straight arrows to relate inputs, reasoning or evaluation, and outputs. It contains no pictograms, photographic, stock or generated-image assets. Run `python supplementary/update_evidence_visio.py` to regenerate its native page, then `./supplementary/export_visio_figures.ps1 -FigureNumbers 7` to export only Figure 7. This update preserves the other six native pages and their PDF exports. The supplied PDFs can be used to compile the manuscript on any OS without Visio.

`protocol-specification.txt` defines the proposed Fabric application, placement, state, endorsement, constrained verification and matched log baseline. `consensus-requirements.csv` records family-specific assumptions and scenario decisions. The schema and byte counts are reproducible; full Fabric envelopes and operational performance require implementation measurement.

## Expanded synthesis and sensitivity

`CODING-DECISIONS.md` documents claim/evaluation distinctions, including weak demonstration cryptography, receiver versus original AIS sender, intended underwater applications evaluated on terrestrial data, positive UAV continuity mechanisms, protocol fault models, and unimplemented PBFT recovery. Profiles describe reported forms, not a quality ranking or independent certification of claimed security.

`analyze_oal.py` validates identifiers, reference-role correspondence, code ranges, locators and duplicate records. It produces eight variants in `oal-sensitivity.csv`, 39 exclusions in `oal-leave-one-out.csv`, descriptive layer co-occurrences in `oal-layer-cooccurrence.csv`, and `oal-analysis-summary.json`. The variants separate direct-domain/transferable studies, remove S35–S38 consensus comparators, remove four conceptual-only studies, remove S34's proxy data, collapse S01–S03 platform identities to entity identities, and treat S31's physical experiment as L3 only. Co-occurrence does not prove a validated handover. These are descriptive stability checks, not confidence intervals or an effectiveness test of OAL.

The full map has 25 occupied cells, with D/G/F largest (16 studies). Without the four generic consensus papers it remains largest (12), and occupancy remains 25. The direct-domain stratum has 18 occupied cells and E/G/A largest (6); the transferable stratum has 20 and D/G/F largest (11). Leave-one-out occupancy ranges from 23 to 25, retaining D/G/F as the largest cell. The sole L4 code belongs to S31's bounded physical UAV-node experiment; a conservative L3-only reading leaves the heatmap unchanged. No L5 or integrated air–surface–underwater validation is inferred. Empty cells also remain distinct from applicability judgments.
